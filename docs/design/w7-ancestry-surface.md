### 1.2 Reduction to region polygons, build time only

Feasible in Node with build-time packages only. None of `topojson-*`, `d3-geo`, `polygon-clipping` is in `package.json` or `pnpm-lock.yaml` today (grep: 0 hits). Proposed devDependencies (build script only, never imported by app code): `topojson-server` (topology + `quantize`), `topojson-simplify` (`presimplify`/`simplify` to a point budget), `topojson-client` (used only by the unit test that round-trips the in-repo decoder), `polygon-clipping` (MIT; union / intersection with stated bounding boxes / difference with named natural features). Script: `scripts/build-region-geometry.ts` (Platform owns `scripts/`; request row in `decisions.md`; the alternative home `data/ref/regions/build-geometry.ts` needs no ownership change). No `package.json` script name is added — X14 (`brief:2514`) closes the script list; the invocation `pnpm exec tsx scripts/build-region-geometry.ts` is documented in `GEOMETRY_PROVENANCE.md`.

Runtime: no map library, no CDN, no tile server, no fetch. A hand-written decoder `src/lib/geo/topojson.ts` (≈60 lines: delta-decode arcs with `transform.scale/translate`, resolve `~i` reversed arcs, assemble rings per geometry) and `src/lib/geo/project.ts` (equirectangular, below) turn the committed `public/geo/regions.topo.json` into SVG path `d` strings. The 110m land file has 5,143 points before reduction; five continental regions after simplification to ≈2,000–3,000 points quantize to well under 60 KB, inside the 180 KB budget (`brief:2318`).

Projection (pure function, unit-tested): viewBox `0 0 1600 900` (16:9, `brief:308`); `x = (λ + 180) × 1600/360`; `y = (84 − φ) × 900/140` for φ clamped to [−56, 84] (Antarctica is excluded from the geometry file, so nothing is drawn below Cape Horn). This is an equirectangular projection with standard parallel ≈ 46° (the y/x scale ratio 1.446 = 1/cos 46.2°), which fills a 16:9 frame without letterboxing; A.8 names equirectangular (`brief:2252`) and does not fix the standard parallel.

Where decoding happens: the server page imports the TopoJSON statically (`resolveJsonModule` is on, `tsconfig.json:12`), decodes and projects it, and passes `{ code, d, bbox, centroid }` per region to the client map component. The RSC payload then carries ≈20–40 KB of path strings and the client bundle contains no geometry code; the file at `public/geo/regions.topo.json` remains the committed, budgeted artifact the brief names. (The alternative — client `fetch("/geo/regions.topo.json")` — adds a loading state and a same-origin request for no benefit; see open decision 12.)

## 3. Uncertainty

### 3.1 What G4.4 requires and what exists

G4.4 (`brief:2631`): the reference panel and version; markers used of required; "an interval, or an explicit statement that an interval is unavailable"; the resolution limit in plain words. A.8's stricter "A region may never be rendered with a point estimate and no interval" (`brief:2254`) presupposes the bootstrap over a sub-continental panel it describes; G4.4 is a gate and X16.6 (`brief:2536`) sends the panel to the science dimension. §4.6 (`brief:308`) says the threshold and its re-derivation belong to the science dimension too. So W7 renders the point with the explicit statement; it does not invent a range (X0.1, `brief:2364`), and it does not persist a degenerate `p05 = point = p95` row in `ancestry_regions`, which the schema would accept but which would read as a zero-width interval.

### 3.2 What renders for each share (copy in `src/copy/ancestry.ts`; U+2019 apostrophes)

Per share, as the `ancestry-share` figure's unit (the sibling node the E2E requires): `RANGE_UNAVAILABLE_SHORT = "no range yet"`.

Once per claim block, beneath the table, always visible (X13):
- `RANGE_UNAVAILABLE = "Inherit can’t put a range on these shares yet, so each one is a single number. When a range can be computed it will appear beside every share."`
- `PANEL_LINE = "Reference panel: 168 ancestry markers from the Kidd and Seldin panels, with 1000 Genomes phase 3 frequencies. Panel built 2026-08-28."` (name and version from `data/ref/AIMS_PROVENANCE.md:1-13`; constants in `src/lib/ancestry/panel.ts`, never retyped.)
- `markersLine(k) = "Your file supplied {k} of the 168 markers this needs. A map needs at least 42."` — 42 is `Math.ceil(RELIABLE_FRACTION × AIMS.length)`; a `coverage` figure (`read: k, needed: 168`) sits inside the same block so the count is a contract figure.
- `RESOLUTION_LIMIT = "Five broad regions is the finest this panel can tell apart. It cannot place DNA within a region."`
- The mandatory identity sentence, once in the block and once in the click panel: `"An estimate of where DNA like yours is common today. It is not a statement about your identity, nationality, or family history."` (`brief:312`).
- The G4.2 marker `MODELLED_MARKER` renders once via `ClaimBlock` (basis `modelled`).

The "marker" gloss: `marker` is in `data/jargon.json`, and "ancestry markers" is inside a mandated §4.6 string, so the page renders a ≤25-word definition on first use (`"A marker is one DNA position that differs between people and helps tell regions apart."`), the escape G1.10/X7.3 grant.

### 3.3 Opacity, hairline, hatch with no interval

X16.5 (`brief:2534`) governs: one encoding, opacity ∝ the interval's lower bound, floor 0.15, hatch where the interval exceeds 0.10, radial-gradient feather ≥ 15% of the bbox width. §4.6's "blur radius of at least 24px" (`brief:308`) is the earlier draft of the same rule and is not implemented as a second encoding.

One function in `src/lib/ancestry/present.ts`: `lowerBound(share) = share.range ? share.range.low : share.point`. Decision and justification: with no interval, the only established quantity is the point, and it is already printed as text beside the map; encoding the same number as opacity adds no claim (accuracy unchanged), while a uniform 0.15 floor for every region would throw away the 60/30/5 story the numbers tell and make the map a locator only (comprehension lost for no accuracy gain — X0.1 order). When a range exists the same function switches to the lower bound and nothing else changes. Hence:
- `fillOpacity = max(0.15, lowerBound)` for `lowerBound > 0`;
- `lowerBound === 0` (a 3-dp proportion of `0.000`) → dashed hairline, no fill (the degenerate range `[0, 0]` "includes zero");
- hatch: never, until an interval exists (`range.high − range.low > 0.10`).

### 3.4 Bands (half-open, on the continuous share, before rounding)

`band(p)`: `p ≥ 0.30` → "a large part"; `0.10 ≤ p < 0.30` → "a noticeable part"; `0.02 ≤ p < 0.10` → "a small part"; `p < 0.02` → "possible but not established" (`brief:314`). Inputs are the stored 3-dp proportions; rounding to one decimal for display never feeds back.

### 3.5 The toggle and the two chips: shown + u + h = 100.0 exactly

- `u_cont = 1 − Σ proportions` = 0 by construction (`admixture.ts:124-127` repairs the sum to exactly 1); rendered anyway, both chips render even at 0% (`brief:316`).
- Toggle "Show only what’s well supported" hides regions with `lowerBound < 0.02`; `h_cont = Σ hidden proportions` when on, 0 when off.
- Naive one-decimal rounding of five regions can drift up to ±0.25 from 100, outside the ±0.1 tolerance, and rounding h as a residual goes negative when the toggle is off. So display values are apportioned once, over the fixed set {5 regions, u}, by largest remainder to one decimal (`apportionShares()`): floor each to 0.1, distribute the leftover tenths to the largest remainders. Properties, unit-tested: Σ display = 100.0 exactly; a region's display value is identical in both toggle states; each display value is within 0.1 of naive rounding; an entry at exactly 0 never receives a tenth. Then `h_display = Σ display of hidden regions` (on) or `0.0` (off), so shown + u + h = 100.0 exactly in both states.
- The `ancestry-share` spec for a row carries `share = display/100` (so the figure prints the apportioned one-decimal value); `band`, `lowerBound` and opacity use the continuous proportion. Known cosmetic edge, accepted: a hidden region at 1.96% may display "2.0%" inside "Hidden as not well supported: 2.0%".
- Chips are `ancestry-share` figures with range unavailable, `data-slot="ancestry-chip"`, labels `"Not assignable to any region: {u}%"` and `"Hidden as not well supported: {h}%"` (`brief:316`), rendered below the map in both states; the E2E distinguishes rows (`data-slot="region-row"`) from chips.

### 3.6 Grey state (below `RELIABLE_FRACTION`)

`markersUsed / 168 < 0.25`: the map renders with every region as a grey outline (`fill: var(--line)` at 0.3, no gradient), no percentages, no toggle, no chips (a chip is a percentage and the brief says "no percentages" for this state — decision to record), and the exact copy `"Your file covers only {k} of {N} ancestry markers — too few to draw a map. This is a limit of the file, not a result about you."` (`brief:316`; em dash U+2014). The counts are rendered inside the mandated sentence with `// inherit-figure-exempt: mandated §4.6 grey-state sentence; a count of positions, not a result figure` (precedent: `decisions.md:160-163`). Raw numbers are one activation away in a `<details>` whose summary stays `"Show the unreliable raw numbers anyway"` (pinned by `e2e/upload-vcf.spec.ts:133`): a `ClaimBlock` rendering a `<ul>` of five `<li>` (pinned count) each with the region name and an `ancestry-share` figure (range unavailable), the stored `support_note` (`"Low confidence: … proportions are unreliable."`, pinned at `:135`) and the sentence `"Treat these as statistical noise, not as an estimate of your ancestry."` This section must contain exactly one list element (the spec's `admixture.getByRole("list")` is strict).
